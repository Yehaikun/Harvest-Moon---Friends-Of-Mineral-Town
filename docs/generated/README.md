# Generated Indexes

This directory stores generated indexes that make ROM/script editing easier to
review. Regenerate them when scripts or map constants change.

## Warp Index

`warp_index.tsv` is generated by:

```sh
make warp-index
```

It scans `scripts/script_*.mary` for `Proc016(map, x, y)` calls and records the
nearest following `SetEntityPosition(...)` call, preferring player entity `0`.

Important columns:

| Column | Meaning |
|---|---|
| `script_id` | Event script ID |
| `line` | Line of the `Proc016` call in the script |
| `map_id` / `map_name` | Destination map from `Proc016` |
| `proc_x` / `proc_y` | Coordinates passed to `Proc016` |
| `entity_id` | Entity positioned after the warp; `0` usually means player |
| `entity_x` / `entity_y` / `facing` | Position passed to `SetEntityPosition` |
| `has_player_position` | Whether a player `SetEntityPosition(0, ...)` was found nearby |

This is a static index. It does not prove when a script is triggered. Use it to
find likely warp scripts, then verify the trigger in game or by reading the
calling script/event table.

## Script Cross References

`script_xref_index.tsv` and `warp_trigger_candidates.tsv` are generated by:

```sh
make script-xref-index
```

The scanner looks for integer arguments in mary function/procedure calls where
the integer is also a valid script ID. This is intentionally conservative:

- `script_xref_index.tsv` contains all candidate references.
- `warp_trigger_candidates.tsv` keeps medium-confidence references to scripts
  that also appear in `warp_index.tsv`.
- The `confidence` column is a heuristic, not proof. Values like `Func03E(167)`
  can be event flags rather than script IDs and are kept only in the full xref.

Use this index to find candidates quickly, then confirm by reading the script or
the relevant engine/table code.

## ROM Warp References

`rom_warp_ref_index.tsv` is generated by:

```sh
make rom-warp-ref-index
```

It scans 4-byte-aligned values in ROM data before the event-script bytecode
region and keeps values that match script IDs in `warp_index.tsv`.

This is useful because some trigger tables are not represented as mary scripts
yet. For example, a door/entrance table may store script ID `167` directly in
raw data. These rows are still candidates: check nearby pointers, map IDs, and
the containing `.incbin` symbol before treating them as confirmed trigger data.

## Decoded Script Table at `gUnk_080F1FC0`

`script_table_080F1FC0.tsv` is generated by:

```sh
make script-table-index
```

The table starts at ROM offset `0xF1FC0` and currently decodes as repeated
8-byte records:

```text
u32 pointer;
u32 script_id;
```

For the chicken-coop test, record `126` points to script `167`. The pointed data
still needs to be named and structurally decoded, but this is a better trigger
lead than generic mary cross references.

Current chicken-coop findings:

| Source | Finding | Confidence |
|---|---|---|
| `warp_index.tsv` | `script_167.mary` warps to `MAP_BEACH` at `(24, 280)` | confirmed by build/decompile/game test |
| `script_xref_index.tsv` | `Proc030(167)` and `Proc008(..., 167, ...)` candidates exist | low to medium; likely talk portrait/action metadata, not door trigger |
| `rom_warp_ref_index.tsv` | `0xF016C` is inside `gArticleInfo` | false lead; item data |
| `rom_warp_ref_index.tsv` | `0xF23B4` is inside `gUnk_080F1FC0` | strong lead |
| `script_table_080F1FC0.tsv` | record `126` is `{ pointer=0x080F2468, script_id=167 }` | strong lead, structure still unnamed |

Analysis confirmed:
- 104 valid entries out of 266 (remaining entries are padding/non-script data)
- NPC interaction scripts (1000-1030 range) are NOT in this table
- gUnk_080F1FC0 is an **entity behavior/script table**, not a dialogue script table
- Entities sharing `data_ptr` (e.g. `0x080f24ec` with scripts 300/840/180) share behavior data but differ in interaction script
- The chicken coop door (entity index 126, script 167) is one of 4 entities sharing `ptr=0x080f2468`
- NPC dialogue scripts are assigned through a separate mechanism (not gUnk_080F1FC0)

### Trigger Chain Summary

The complete trigger chain for map entrances:

```text
Map Tile Data (per-map baked)
  → contains entity type index for interactive tiles
  → e.g. chicken coop door tile → entity type 126
      ↓
gUnk_080F1FC0[entity_index]
  → { data_ptr, script_id }
  → gUnk_080F1FC0[126] = { ptr=0x080F2468, script_id=167 }
      ↓
Event Script
  → script_167.mary: Proc016(MAP_BEACH/MAP_MOTHERS_PEAK, ...)
  → runs the actual warp/event
```

The entity type → map tile mapping is baked into each map's tile data
(MP format), not stored in a centralized table. This means modifying
which entity appears on a map requires editing the map's tile data itself.

## Map Master Index

`map_master_index.tsv` is generated by:

```sh
make map-master-index
```

It combines map constants, warp scripts, spawn coordinates, and current map data
candidates into one review table. Use it before any map experiment to answer:

- which `map_id` belongs to a target area,
- which scripts warp into that map,
- which coordinates are already known to be safe,
- which candidate data records are associated with the map.

The `collision_candidate_offset` column is intentionally named as a candidate.
It currently points at a 0x80-byte map-indexed record, not a verified 64x64
collision grid.

## MapData Table

`map_data_table.tsv` is generated by:

```sh
make map-data-table
```

It decodes the table used by `GetMapData(map_id)`:

```text
gUnk_08105EDC + map_id * 0x28
```

Important columns:

| Column | Meaning |
|---|---|
| `packed_img` / `packed_tiles*` / `packed_pal*` | compressed visual resource candidates |
| `terrain_info` | terrain/collision/action info array candidate |
| `terrain_map` | per-tile terrain index map candidate |
| `width` / `height` | map dimensions in tiles |
| `is_interior` | whether the map is an interior |

This is currently the strongest known route for map expansion work.

## Collision / Boundary Candidate Exports

Read-only candidate exports are generated by:

```sh
make collision-candidate-farm
make collision-scan-popuri
```

Outputs are written to `docs/generated/collision/`.

These files are for reverse-engineering only. They do not patch the ROM and do
not prove that the candidate records are the final movement collision data.
