FoMT 地图相关函数排查记录
==========================
更新日期: 2026-06-05

结论摘要
--------
`func_08050D34` / `func_08050D3C` / `func_08050DC8` / `func_08050DF0` /
`func_08050E30` 暂时不应作为地图扩展主线目标。

原因:
- 它们都在 `asm/code_0803EE94.s` 中。
- `func_08050DC8` 是 `func_08050424` 的包装器。
- `func_08050E30` 是 `func_08050664` 的包装器。
- 底层函数大量调用 `strlen`、使用默认字符串 `gUnk_080F9F3C`、并把字符串送入
  `func_080ADD5C` / `func_080ADD74` / `func_080ADD78`。
- 这些行为更像文字窗口、菜单或 UI 消息对象, 不是地图视觉/碰撞/边界加载。


已排除的误判
------------
之前计划里把以下符号列为地图加载候选:

```text
gUnk_080E86C0
gUnk_080E878C
gUnk_080E87A4
gUnk_080E87FC
gUnk_080E8828
gUnk_080E8878
func_08050DC8
func_08050E30
```

当前判断:
- 这些 `gUnk_080E8xxx` 符号在 `new_game.s.orig` 中用于新游戏/存档选择界面文字。
- 它们不是地图 tilemap/collision/resource 表。
- `func_08050DC8` / `func_08050E30` 负责显示这些文字或构造相关 UI 状态。


关键汇编证据
------------
`func_08050DC8`:

```asm
ldr r0, [r0]
bl func_08050424
```

`func_08050424`:

```asm
adds r4, r5, #0
adds r4, #0xec
adds r0, r4, #0
adds r1, r7, #0
adds r2, r6, #0
bl func_080ADD5C
adds r0, r4, #0
mov r1, r8
bl func_080ADD74
movs r0, #4
str r0, [r5, #8]
```

`func_08050664`:

```asm
bl strlen
...
ldr r7, =gUnk_080F9F3C
...
bl func_080507F8
```

这些不是地图数据解包流程的形态。


下一步正确方向
--------------
地图扩展需要优先找这些链路:

1. 当前 map/room ID 从哪里读出。
2. map_id 如何映射到 tilemap、碰撞、边界、实体触发记录。
3. 0x120BBC + map_id * 0x80 这组候选记录由哪个函数读取。
4. 玩家移动时如何查询“下一格能不能走”。
5. 镜头边界如何根据当前地图设置。

更合适的候选搜索方式:
- 先找读取当前 map/room ID 的函数。
- 再找读取地图候选记录的函数。
- 再找移动碰撞判定函数。
- 最后才做 C 反编译, 不先对 UI 包装函数动刀。
